# 衡的回应 — 第13轮

我先把最重要的一句话放在前面：

**不要一开始就相信“三端通吃”的网络效应。**

那是第二阶段甚至第三阶段的故事，不是独立开发者第一阶段的落地逻辑。

如果现在就按“原告端、企业端、律师端互相导流”来设计，最后大概率会变成：

- 功能太散
- 合规边界太乱
- 数据不够深
- 一个也做不成

所以我的判断会非常收窄。

---

## 议题一：先做哪一端？

### 结论：**先做企业端，但只做一个极窄版本**

我的优先级排序是：

1. **B 端企业端**
2. **律师端**
3. **原告端**

### 为什么不是原告端

因为原告端最容易踩进两个坑：

1. **法律服务边界最敏感**
   “教你怎么告”“帮你判断能不能告”“生成起诉状”这类表达，最容易被理解成正在提供具体法律建议。

2. **情绪型用户最多，履约成本最高**
   原告端用户通常更急、更情绪化、也更容易把平台理解成“帮我赢”的承诺。

这对第一版产品非常危险。

### 为什么不是律师端

律师端并不是不能做，而是：

- 中国大陆已有很多成熟工具
- 律师用户对准确率、证据链、类案质量极敏感
- 没有强数据壁垒时，很容易被对比到现有老玩家面前

更现实地说：

**律师端更像一个需要多年积累和深行业关系的产品。**

它以后可以做，但不适合做第一枪。

### 为什么先做企业端

因为企业端最容易满足三件事：

1. **付费逻辑清楚**
   企业愿意为“少踩一个法律坑”付钱，这比个人用户为“我要不要告”付钱更稳定。

2. **边界更好守**
   你可以明确定位为：
   - 风险预警
   - 公开信息整合
   - 诉讼成本估算
   - 一般性应对路径

   而不是具体法律意见。

3. **更适合从窄场景切入**
   你不需要服务所有企业，
   只需要服务一类企业：

   **“中国出海到某地的小企业/小团队，在进入市场前和被卷入纠纷前，想先看风险。”**

这就足够形成第一版产品。

## 议题二：先做哪个市场？

### 结论：**先做新加坡，不做中国大陆，不做韩国首发**

我的排序是：

1. **新加坡**
2. **香港**
3. **韩国**
4. **中国大陆**

### 为什么是新加坡

不是因为它最大，
而是因为它对第一版产品最友好。

我看重的是四个条件：

1. **英语环境**
   这对独立开发者太关键了。你不需要一开始就同时解决韩语/日语/本地客服问题。

2. **公开数据可用性较好**
   公司注册、法院判决、监管处罚等公开数据更容易形成可抓取、可整理、可解释的基础层。

3. **可以“坐在中国服务境外”**
   不需要 ICP，不需要先把产品绑死在国内法律科技监管环境里。

4. **客户画像清楚**
   最适合的第一批客户不是新加坡本地大型企业，
   而是：

   **中国团队、独立开发者、小型 SaaS / AI 工具团队，准备进入新加坡或已在新加坡运营。**

这批人离诚卓更近，也更可能成为真实首批客户。

### 为什么不是中国大陆

因为中国大陆不是不能做，
而是第一版就做大陆，会一下背上最重的包袱：

- ICP
- 法律服务边界更紧
- 企查查/天眼查/吾律/AlphaGPT 等成熟竞品
- 用户对“法律相关服务”的敏感度和预期都更高

你会一上来就进入红海中的重合规区。

这不适合独立开发者开局。

### 为什么韩国不适合作为第一个法律AI市场

和第 11 轮一样：

- 语言门槛高
- 本地化重
- 合规理解成本高

韩国以后可以做，
但不适合做第一版法律 AI 产品的起点。

## 议题三：MVP 长什么样？

### 结论：MVP 只做两个功能

产品定义我建议写成：

**“面向中国出海新加坡企业的法律风险预警与诉讼成本估算工具。”**

不要写成三端平台。

第一版核心功能只做两个：

### 功能 1：企业法律风险快照

用户输入：

- 公司名
- 注册号
- 或目标合作方名称

输出：

- 历史诉讼/纠纷记录摘要
- 监管处罚或风险公开记录
- 风险标签（合同、劳动、知识产权、数据、消费者投诉等）
- 一个很克制的风险等级

注意：

**不要一开始就吹“预测诉讼”。**

第一版更应该写成：

**“基于公开数据的风险快照与结构化预警。”**

### 功能 2：诉讼成本与应对路径估算器

用户输入：

- 案件类型
- 标的额区间
- 法域（先只支持新加坡）
- 自己当前是原告/被告还是潜在纠纷方

输出：

- 预计律师费范围
- 预计时间范围
- 常见流程节点
- “现在最该先做什么”清单

这个功能比“AI 帮你分析法律问题”更适合第一版，
因为它更像：

- 信息工具
- 决策辅助

而不像：

- 具体法律建议

### 技术栈建议

我和默方向接近，但我会再收窄一点：

| 层 | 选择 | 原因 |
|----|------|------|
| 前端 | `Next.js` | 快速、SEO友好、适合内容页和工具页 |
| 后端 | `FastAPI` | 抓取、解析、AI调用都方便 |
| 数据库 | `PostgreSQL` | 结构化存储企业、案件、标签 |
| 缓存/任务 | `Redis` + `Celery/RQ` | 跑抓取和定时更新 |
| AI | `GPT/Claude` 按任务选用 | 先做摘要、标签、解释，不做核心事实生成 |
| 部署 | 海外 VPS / Railway / Fly.io | 先避开国内备案链路 |

### 数据从哪来

第一版只做**公开数据**，不碰私域材料。

优先数据源：

- 新加坡 ACRA 公开可获取企业信息
- 法院公开判决/案件摘要
- 监管处罚公告
- 公司官网/新闻公告中的公开披露

重点不是“全”，
而是：

**先把一小组稳定的数据源吃透。**

### 收费模式

我建议比默更保守一点。

第一版不要急着做复杂订阅层。

先做：

- `免费版`：有限次数快照查询
- `Pro 单人版`：`$19-$29/月`
- `报告版/顾问版`：按次收费，`$99-$299/次`

为什么要加按次收费？

因为第一批客户很可能不是要长期每天查，
而是：

**“我现在正准备进市场/签合作/处理一个风险，先买一次看看。”**

这类客户对按次买单更友好。

### 上线时间

如果真收敛到这两个功能，我的判断是：

- `2周` 数据源验证
- `2周` MVP 开发
- `1周` 自测与小范围试用

**5周可以出第一版。**

但前提是：

- 不做三端
- 不做复杂预测
- 不做大而全的 AI 法律顾问

## 议题四：合规和利益冲突怎么解决？

### 结论一：第一阶段不要三端通吃

这个问题最简单的解法不是写一堆条款，
而是：

**先不要同时服务原告端和被告端。**

我的建议是：

- 第一阶段：只做企业端
- 第二阶段：如果要做律师端，作为独立产品线或独立模块
- 原告端最后考虑，甚至可以永远不做

因为只要原告端一进来，
你立刻会遇到最难回答的问题：

- 同一案件两边都来怎么办
- 你是在帮助维权还是在引导诉讼
- 你的数据和建议会不会被视为偏向某一方

对第一版来说，这些都太重。

### 结论二：定位必须是“法律信息服务”，不是“法律服务”

这一点要写得非常死。

可以做的：

- 公开数据检索
- 风险标签和信息整合
- 案件流程说明
- 成本范围估算
- 一般性应对清单

不能做的：

- 具体案件胜负判断
- 明确建议“该不该起诉/该不该和解”
- 代替律师出具法律意见
- 伪装成律师或律所

### 结论三：界面和文案上必须把边界写清楚

不是藏在用户协议里，
而是显性化：

- 本产品提供公开信息整理与风险辅助判断
- 不构成律师意见
- 复杂或具体案件应咨询持牌律师

这类提醒会损失一点“万能感”，
但能保住长期可信度。

### 结论四：利益冲突的真正解决办法是“阶段隔离 + 数据隔离”

如果未来真的扩到多端，
我的建议是：

- 产品线隔离
- 数据权限隔离
- 用户协议隔离
- 案件级冲突隔离

甚至必要时：

**宁可用两个品牌，也不要在同一个产品壳里同时做原告与被告端。**

因为法律相关产品一旦失去中立信任，
死得会非常快。

## 最后收束

如果要我把这轮收成最短的执行版建议，我会这样写：

### 我的最终建议

- **先做哪端**：企业端
- **先做哪个市场**：新加坡
- **MVP 是什么**：企业法律风险快照 + 诉讼成本估算器
- **定位是什么**：法律信息服务，不是法律服务
- **收费怎么做**：免费查询 + 月订阅 + 按次报告
- **多久上线**：5周
- **利益冲突怎么解**：第一阶段不碰原告端，只做企业端

我最想强调的一句是：

**不要先做一个“三端平台”。**

**先做一个“能帮中国出海团队在新加坡少踩一个法律坑”的窄工具。**

只要这个窄工具有人愿意付钱，
三端才有未来。
