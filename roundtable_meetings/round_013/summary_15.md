# Round 013 Turn 15 总结 — 技术架构：支付、部署、语言

**议题**：FreezeGuard V1 的技术选型——支付接入（个人能不能用）、后端部署（哪里、怎么部署）、数据库、开发语言。

**参与者**：默（Claude）、衡（ChatGPT）、豆包（Doubao） | 问（Qwen）本轮仍离线

## 一、共识（3/3 一致同意）

### 1. 开发语言：TypeScript 全栈

所有人一致同意 **TypeScript** 是 V1 的最佳选择。

- 前端 Next.js + 后端 API Routes 全用 TypeScript，一种语言搞定全栈
- **不用 Python**（V1 不需要 AI/ML）
- **不用 Java**（太重，独立开发者 5 周出不了活）
- **不用 Go**（过度设计，V1 根本不需要这种并发性能）
- V2 需要 AI 时，Python 作为独立微服务通过 API 对接即可

### 2. 部署：Vercel + Supabase

所有人一致同意 **Vercel（前端+API）+ Supabase（数据库+认证+存储）** 作为首发部署方案。

- V1 月成本 **$0**（免费层完全够用）
- **不推荐阿里云/腾讯云**（需 ICP 备案、内容审查风险、"帮你起诉亚马逊"可能触发敏感词）
- **不推荐 AWS Lambda**（配置复杂、冷启动慢、对独立开发者不友好）
- **不推荐买服务器**（V1 全是短请求，不需要 24 小时跑着的 VPS）

### 3. 数据库：Supabase（托管 PostgreSQL）

所有人一致同意 Supabase 一站式方案。

- PostgreSQL 数据库 + Auth 认证 + Storage 文件存储 + 自动 REST API
- 6 张表搞定全部需求（users, cases, assessments, tasks, evidence, payments）
- 不用 DynamoDB（AWS 锁定）、不用 MongoDB（结构化业务数据没优势）

### 4. 最终技术栈

```
TypeScript + Next.js + Tailwind CSS + Vercel + Supabase + Stripe/Paddle
```

**V1 月成本：~$1/月**（只有域名费用，其他全在免费层内）

## 二、关键补充与风险（衡和豆包的修正）

### 支付——最容易被"说轻"的一环

**衡的核心警告**：支付不能想成"都能接"，而要想成"**先保住一条可用主路径**"。

| 风险点 | 说明 | 提出者 |
|--------|------|--------|
| **Stripe 港卡中转不一定顺畅** | 频繁接收跨境维权款项可能被银行限制非柜面交易，年度结汇额度限制 | 豆包 |
| **支付宝当面付有限额** | 个人商户有单日/单笔限额，境外用户支付宝付款成功率不稳定 | 豆包 |
| **税务合规空白** | 个人收款通道未做税务申报，后续有个税/海外税务稽查风险 | 豆包 |
| **无应急备用支付通道** | Stripe/支付宝被风控就直接切断付费转化 | 豆包 |
| **退款和争议处理没想清楚** | 用户付了 $99 但不满意怎么办？ | 衡 |
| **中国用户在微信里看到美元支付页直接退出** | 转化率杀手 | 衡 |

**衡的支付策略**：
- **第一阶段**：只保住一条主路径（Stripe 或 Paddle），让愿意付国际支付的人能付
- **第二阶段**：再补国内路径（支付宝/微信）
- **衡更倾向 Paddle 作为首发**：虽然手续费 5%，但帮处理全球税务、退款、发票，业务上可能比 Stripe 更省事

### 部署——需要备用方案

| 风险点 | 说明 | 提出者 |
|--------|------|--------|
| **Vercel 在中国部分地区访问慢** | 需叠加 Cloudflare CDN 优化 | 豆包 |
| **微信内打开 Vercel 域名可能被拦截** | 需配置独立 SSL 域名 | 豆包 |
| **网络波动不可控** | 必须准备 Cloudflare Pages 或香港/新加坡 VPS 作为备份 | 衡 |

**衡的态度**：Vercel 可以首发，但不要当成"永远稳定的默认答案"。架构上要提前想好"如果 Vercel 某天不稳，我怎么切"。

### Supabase——好用但要防锁定

**衡的警告**：把 Supabase 当成"托管 Postgres + 辅助服务"，**不要**当成"平台会替你设计系统"。

- 业务规则不要写死在平台特性里
- 表结构要足够清楚
- 状态机逻辑留在应用层可读
- 从第一天就按"**未来能迁**"来设计

## 三、遗漏的关键技术问题

衡和豆包各自补充了我没覆盖到的重要维度：

| 问题 | 说明 | 提出者 |
|------|------|--------|
| **日志与审计** | 用户提交了什么、系统按什么规则判了什么、什么时候解锁了哪步——必须可回溯 | 衡 |
| **规则/模板版本管理** | 平台政策会变，必须知道某个用户看到的是哪一版结果 | 衡 |
| **规则引擎热更新** | 平台规则变动时，后台一键更新，不需要重新发版 | 豆包 |
| **前端性能** | 用户最慌的时候点击等 4 秒、支付跳转卡，转化直接掉 | 衡 |
| **邮件与通知** | 支付成功邮件、结果回执、时效提醒、进度提醒——V1 至少轻做 | 衡 |
| **跨境数据合规** | 用户案件数据需符合 GDPR/CCPA，Supabase 需选对存储区域 | 豆包 |
| **数据灾备** | Supabase 自动备份不够，需配置每日自动导出 | 豆包 |

## 四、分歧点

### 支付首发选 Stripe 还是 Paddle？

| 观点 | 支持者 |
|------|--------|
| Stripe 首发（更主流、手续费低 2.9%） | 默 |
| Paddle 首发（帮处理税务退款、业务更省事、个人直接申请） | 衡倾向 |
| 两者都可，但必须有备用通道 | 豆包 |

### V1 是否要做国内支付（支付宝/微信）？

| 观点 | 支持者 |
|------|--------|
| V1 就做（支付宝当面付零门槛） | 默 |
| V1 先不做，第二阶段补（先保住一条国际支付主路径） | 衡 |

│                                              │
